# Doit: Design

2026-11-20 · Tabu

What the app is now. The source of truth for what gets built. When code and this document disagree, one of them changes in the same commit and the Changelog says which.

## Purpose

One local board where Tabu and Claude share every project's epics, tasks and bugs, so Jira and Confluence can be cancelled. Claude reaches it through a CLI that returns only the slice it asks for. Left out for now: the Confluence import, a later epic. The Marketing view (section Marketing) has game profiles and contacts; mail, festivals and campaigns are not built yet. The wireframe for all of them is `Docs/Design/wireframe.html`.

## Users and their jobs

- **Tabu** opens the board to see what to do next, what Claude is doing, and to rank, add, comment on and close work. Done for them: the next thing to do is at the top of Active, and Claude's work is one click away.
- **Claude** asks the CLI for open tasks in one project or epic, works the AI tasks top to bottom, comments on progress and closes them. Done for Claude: it never reads more than the slice it needs, and never reads the archive.

## Projects

- A project is a folder with a docs folder inside, `Docs/` by the standard; a project that has not renamed its own yet (`BB-Docs/`) is registered with that name. The project list lives in the app's settings, not in any project.
- **+ New project**, the last row of the Projects menu, asks for a name, a folder and the docs folder name. It creates `<docs>/Epics/` with `Tasks/`, `Parked/` and `Completed/` where missing, and a rolling bug epic `EPIC-001: Bugs (rolling)` when the project has no epics yet. It never overwrites an existing file.
- The top bar shows **All projects**, then the starred projects, then a **Projects ▾** menu listing every project. In the menu a click on a name selects the project; a click on its star pins it to the top bar or takes it off. The star is kept in the settings file. A selected project without a star shows its name on the menu button. In All projects each row shows a project pill.
- **Kind.** A project is a `game`, an `application` or a `podcast`, or has no kind. It is set on the project: the project's settings (the gear), or `doit project set <id> kind=game` (`kind=` clears it). It is kept in the settings file beside the star, since the project list lives there. Marketing reads it: every game, application and podcast is offered in the Marketing picker, and the kind is the profile's kind.
- **Project settings.** In the left pane, a **gear icon** right of the project's name opens that project's settings in the middle and right columns, in place: the top-bar view does not change (Board stays selected) and there is no Settings button in the top bar. A second click on the gear, or selecting a task or epic, brings the task layout back. The settings hold the project's kind, a **Marketed** switch and, for a marketed project with a kind, its marketing profile (genres, platforms, stage, release date, what it needs now; Marketing, step 1). The kind is written to the settings file as soon as it is picked; **Save** writes the profile to `<docs>/Marketing/Profile.md`, creating the file from the template when it is missing. The Projects menu has no kind select.
- **Marketed.** A project with a kind is marketed unless told otherwise. A **Marketed** switch in its settings, or `doit project set <id> marketed=no` (`marketed=yes` undoes it), marks it not marketed: it keeps its kind but leaves the Marketing picker, the + Campaign project list, Overview and fit. The flag is kept in the settings file beside kind and star. Doit, Day Drop and HBD Shorts are not marketed for now.
- **Project page.** A project's name in the left pane is a button. A click shows the project page in the Detail column and clears the selected task and the epic filter; choosing a task or an epic replaces the page. With one project selected in the top bar and nothing chosen, the Detail column shows that project's page in place of "Select a task." In All projects that line stays until a name is clicked. Top to bottom:
  - A header line, `PROJECT · <id> · <kind>`, with a **Settings** button that opens the project's settings as the gear does. Under it the project's name.
  - **In short**: the first `In short:` line of the project's design doc (`Design/GameDesign.md`, else `Design/Design.md`), with the doc's `Now testing:` line under it when it has one. A project without an `In short:` line gets a line saying where to write it.
  - Three cards. **Active epic**: its name, id and "n of m done". With no `Active` epic it reads "None active", and an `Active` epic whose only open task is its Check in play task does not take the card. **Waiting on you**: the count of the designer's open tasks and the epics they are in, in the designer's warm colours (section Look). **Planned next**: the count of `Planned` epics, and "n parked".
  - **Waiting on you**: the designer's open tasks, one row each: id, bold title, a You chip. A row opens the task. A designer's task that an open task blocks is not waiting yet. That keeps a Check in play task off the list until the build is done: the planner sets `blocks` on the last build task.
  - **Epics** in build order, one row each: id, name, status, a progress bar and "done/total", or "no tasks". A row opens the epic. Build order: the `Active` epic first, then the `Planned` epics, each after the epic its `Order: after EPIC-<nnn>` line names and by number where no line says otherwise, and epics without tasks last.
  - **Parked**: the parked epics folded to one row that lists their names. Opened, it shows one row each.
  - **Documents**: links to the documents the standard names, where the project has them: the design doc, `Architecture.md`, `Playtest.md`, `UIRules.md`. A link opens the document as any doc opens (section Docs); documents keep their format.

## Epics

- Epic files follow `Docs/Standard/Core/01-Tasks.md`: `<docs>/Epics/EPIC-<nnn>-<short-name>.md`, status `Parked | Planned | Active | Done`, a `## Tasks` checklist.
- The left pane lists the project's open epics (`Epics/`, status Planned or Active) with done/total counts and a progress bar.
- **Clicking an epic** filters the task list to its tasks and shows the epic page in the Detail pane. It works for any epic in the list, parked ones too. Nothing on the page is edited in place; the epic's text is edited through Open file. Selecting a task shows the task in the Detail pane, and clicking the epic again brings its page back. Clicking the epic while its page shows, or **Show all**, clears the filter.
- **The epic page**, top to bottom:
  - The pane header: `EPIC · <id> · <STATUS>`, with **Open file**, **Close epic** on an open epic and **Add contacts** on a campaign. Open file shows the epic's file as a document (section Docs), where it can be edited.
  - Under the title: a status chip, a progress bar with "n of m tasks done", and two counts of open tasks, one for Claude and one for the designer. The designer's count adds "after .n" while an open task blocks the designer's task ("1 for you, after .15").
  - **In short**: the `In short:` sentence in larger type, the `Why it exists:` line under it.
  - A facts grid, label then value: Design, Order, Source and related epics. Every other `Key: value` line of the header shows in the grid too, in file order. An epic id in a value opens that epic.
  - A campaign epic's `Goal:` line is its In short text, and its other brief lines (section Marketing) show in the facts grid.
  - **What changes**: the findings, under a count line ("16 findings · 14 decided · 2 proposed"). One folded line each: number, kind tag, bold title, a Decided or Proposed chip. A click opens the finding's labelled detail (Seen, Cause, Decided). All findings start folded, and what is opened stays open while the epic shows.
  - **Tasks**, as a table: id, title, who (You or Claude), model and effort. The checklist is not shown as checkboxes. A designer's row shows in the last column where it stands: the day it was done, or "after .n". A done row is muted. A row opens the task.
  - **Test plan**: each batch line of the template's form (`Batch A: T-<nnn>.1 to .4 (<modules>)`) as a row of batch, task range and modules, with the Performance and Close lines under it.
  - **Notes**, **Close audit** and **For the standard**: one folded row each, with a note when empty ("none yet", "filled at close"). The Notes row shows what the section holds. Notes kept in a sibling file (`EPIC-<nnn>-<name>.notes.md`, one project's practice and not the standard's) are not shown, and such a file is never listed as an epic.
  - The page has no Check in play section. The checks are a task, the one the Test plan's `Check in play: T-<nnn>.<n>` line names.
- **Epics written the old way** render without breaking; the fallback is plain markdown. No text of an epic file is hidden: what the page cannot place is shown as markdown, in file order. Per part:
  - No `In short:` line: the `Goal:` line is the In short text. Neither: the block is left out.
  - A placeholder value (`<...>`) reads as not written.
  - A Status line with words after the first: the chip shows the word, and the rest shows as a line under the header.
  - Free text in the header: shown as markdown under the facts grid.
  - A finding written as one paragraph: its folded line is its tag and bold title, its chip comes from the first `Decided:` or `Proposed:` in the text, and the paragraph shows when it is opened. A numbered section that has no bold titles shows as markdown.
  - A `## Check in play` section, and any section the page does not know (`Specification`, `Touches`, `Classes`): shown as markdown where it stands.
  - A Test plan line that is not a batch line: shown as markdown.
  - The markdown renderer reads one level of nested list, so a finding's labelled lines read right on the epic page and in a document alike. Before, each nested line got its own number.
- **Close epic** in the epic page's header (open epics only) asks for confirmation, then does what `epic close` does: archives the epic's completed tasks, sets it Done, writes `Closed: <date>` under its status line and moves it to `Epics/Completed/`. Its open tasks are not archived: they stay as they are and are hidden (below).
- **Open tasks of an epic that is not open are hidden.** An epic is open while its file is in `Epics/` with status Planned or Active. While it is parked, completed or archived, its To-do, In progress and Backlog tasks are left out of the Open tab, the project page's waiting list, the Claude view and its due badge, the morning report, the weekly outreach list and `doit list`. Parked means the work is not wanted now, so its tasks are offered nowhere.
  - Nothing is written: the task files and their states stay as they are. When the epic is back among the open epics, the tasks show again, each in the state it had.
  - They are found by asking for the epic. Clicking it in the left pane lists them, under a line that says why they show only there and how to bring them back. `doit list --epic EPIC-<nnn>` lists them and `doit show` returns one, with a line saying it is hidden.
  - Completed and Archived tasks are not affected, and the sweep still archives a hidden task whose deadline passes.
- **Closing waits for the Check in play task.** `doit epic close`, the Close epic button and a drag onto Completed or Archived are refused while that task is open, with a message that names the task. The close hides every open task of the epic, so an unchecked epic would drop off the designer's waiting list at the close. The task is the one the Test plan's `Check in play: T-<nnn>.<n>` line names; an epic without that line closes as before. Once the task is done or archived it no longer holds the close.
- Below the open epics, per project, the left pane has three sections, each folded until its header is clicked, with a count. **Parked**: epics in `Epics/Parked/`. **Completed**: epics in `Epics/Completed/` closed within the keep setting (14 days, the same as completed tasks), newest first. **Archived**: older ones, those with no `Closed:` line, and those with an `Archived:` line. All open the epic's page like any epic; only open epics have Close.
- **Moving an epic by dragging.** An epic button drags onto a section header or onto the open epics:
  - onto **Parked**: status Parked, file moved to `Epics/Parked/`. Planned epics only; an Active epic is refused with a message, since it has a worktree and branch.
  - onto **Completed**: the same as Close epic, with its confirmation.
  - onto **Archived**: Close epic, plus an `Archived: <date>` line under `Closed:`, so it shows in Archived at once.
  - onto the **open epics**, from Parked: status Planned, file moved to `Epics/`. From Completed or Archived it is reopened: status Planned, the `Closed:` and `Archived:` lines removed, file moved to `Epics/`, and the tasks that closing archived (reason `Epic <id> closed`) come back, the ticked ones as Completed and the rest as To-do. Open tasks the close left alone were never archived and show again in the state they had.
  - A drop where the epic already is does nothing. A folded section header opens when an epic is held over it for a moment, so passing over one on the way to another does not move the target.
- The CLI's `epics` lists open epics only; Claude never reads closed or archived ones unless asked.
- **An epic with a worktree** on its branch `epic/<nnn>-<short-name>` has its epic file and task files read and written in that worktree, by the page and the CLI alike, so a tick made during the epic lands on its branch and the main checkout stays clean. When the worktree is removed, they are read from the project folder again.
- **+ New epic** and `doit epic add` create the next number, status `Planned`, with the header the standard asks for: `In short:` and `Why it exists:` placeholder lines, a blank line, then `Status:` and `Design:`. The sections are Findings, Tasks, Test plan, Notes, Close audit and For the standard. A campaign epic keeps its `Game:`, `Event:` and brief lines under `Status:`, and gets no `In short:` line while it has a `Goal:` line.

## Tasks

- A task is a line in its epic's checklist, `- [ ] T-<nnn>.<n> <title> (done when: <check>)`, plus an optional task file `<docs>/Epics/Tasks/T-<nnn>.<n>.md` holding its fields, description and comments. A task without a file uses defaults:
  - state: unticked in an `Active` epic is To-do; unticked in a `Planned` or `Parked` epic is Backlog; ticked is Archived (it was finished before Doit existed);
  - owner: AI; type: Bug when the epic's name contains "bug", else Task;
  - rank: the epic number times 1000 plus the task number.
- Fields: state, owner (`ai` or `human`), type (`task` or `bug`), rank, deadline (optional date), blocks (optional, the task this one holds up, `T-<id>`), created, updated, completed (timestamps).
- **Who builds it.** A task also has agent, model and effort, all optional: the agent that does it (free text, such as `batch-builder` or a session), the model it runs on (free text, such as `Sonnet 5.5`; the page suggests the models the standard names) and the effort (`low`, `medium`, `high`, `xhigh` or `max`, anything else is refused). They are kept in the task file and say something only about a task Claude does. On a task owned by a human the page shows them greyed (Detail pane, below), the CLI's plain text leaves them out, and the stored values stay as they are: changing the owner to human and back brings them back unchanged. `--json` always carries all three.
- States: To-do, In progress, Backlog, Completed, Archived.
- **Open tab:** one column in two sections. Active (To-do and In progress) on top, ranked; Backlog below. A pill on each Active row shows To-do or In progress; clicking it switches. Rows are reordered and moved between sections only by dragging the dotted handle (Alt + arrow keys from the keyboard). Open tasks of a parked, completed or archived epic are not listed until that epic is selected (section Epics).
- **Completed tab:** completed tasks, newest first, each with Reopen. A completed task moves to Archived after **14 days** (setting, 1 to 90).
- **Archive tab:** archived tasks, each with Restore. Claude never reads the archive.
- A task whose deadline passes before it is completed is archived at once.
- Ticking: Completed and Archived-after-completion tasks are ticked `[x]` in the epic file; the others are unticked.
- Archiving moves the task file to `<docs>/Archive/Tasks/`; restoring moves it back.
- Row, left to right: drag handle, rank (Active only), a red dot for a bug or a blue dot for a task, number, title, then on the right: state pill, due date, project pill (All projects), 🧑 or 🤖.
- Search filters by number or text. **All / 🧑 Mine / 🤖 Claude's** filters by owner. The funnel filters by type (tasks, bugs) and due date (any, due within 7 days, has one, has none).
- **+ Task** creates a task in a chosen epic with title, type and owner, at the bottom of Active.
- **Detail pane, the task page.** Top to bottom: the id line (number and epic), the title, chips (type, owner, project), the properties box, Description, Done when, Comments. The layout is the same for both owners; only the description text differs, and that is a writing rule. Text size A− / A+, 12 to 22 px, starting at 15.
  - The properties box shows every value as a control that can be changed. A line in the box says: "Change any value here. Claude changes the same fields with `doit set <project>/<T-id> key=value`."
  - **State**: a dropdown with the five states, Archived among them since a task can hold it.
  - **Owner** (Me, Claude) and **Type** (Task, Bug): toggles as wide as the dropdowns, their two buttons equal halves.
  - **Deadline**: a date picker that always shows, and "Archive when passed". The tick is no field of its own: it is ticked while a date is set, and unticking it clears the date.
  - **Blocks**: the task this one holds up.
  - **Agent**, **Model** and **Effort**: live when Claude owns the task. While the designer owns it they are greyed with "used when Claude owns it", and the stored values stay. Model is free text with the four suggested models, since model names change with each release. Effort keeps `max`, the level only the designer sets.
  - **Created** and **Updated** are read-only and marked "set by the board". After Updated, each shown when set: Contact, Completed, Source, Archived.
  - **Description**: rendered as markdown, whatever its shape, a `For:` line included. A click on it or on **Edit** turns it into a text box. A description that opens with the three story lines gets "As", "I want" and "so that" in bold; the stored text is not changed.
  - **Comments**, with author and time, keep the text box, its placeholder and a **Comment** button.
- **Long titles.** A title over 90 characters is a spec written on the checklist line. The page shows its first sentence (up to 90 characters, cut at a word with … when no sentence ends in time) as the heading and in list rows, and the rest under the heading as the **Spec**, rendered as markdown. Search still reads the whole title, and the epic file is never rewritten for this. New tasks keep the title short and put the spec in the description.
- **Column widths:** dragging the gap between two columns resizes them; the middle column takes what is left. Double-click a gap to reset it. Focused, a gap moves 20 px with the arrow keys. Widths are kept per browser. Below 1100 px wide the layout stacks and the gaps do not drag.
- **Live updates.** A change on disk shows on the page within about a second, with no refresh: a task, epic or doc changed through the CLI, by Claude editing a file, by git, or in another browser tab. The server watches each project's docs folder, the docs folder of each epic worktree, and the app's data folder, and tells every open page that something changed; the page then reloads what it shows.
- A reload waits while Tabu is typing in a text field, dragging, or has a menu or a new-item form open, and runs as soon as that ends. A focused dropdown or checkbox does not hold it.
- When the server stops and comes back, the page reconnects by itself and reloads once.

## Docs

Each project's docs folder (design, specs, architecture) is read and edited in place on the Board, since a doc always belongs to a project. Doit keeps no copy. Claude edits docs as files, as it does today; the page is for Tabu.

- **Epics and Docs in the left pane.** Two buttons, **Epics** and **Docs**, sit in the header of the left pane, right of the title Projects. They apply to every project shown, not one project, and are kept per browser. Both start on. Each project's part shows its name with the gear, then, with Epics on, an **Epics** headline over the epic list and its sections; with both on, a rule and white space; then, with Docs on, a **Docs** headline over the doc tree. With both off a line says to turn one on. Doc trees are loaded only while Docs is on.
- **Opening a doc** gives the document the middle and right columns together, with **Linked** beside it at the right. Selecting a task (in Linked, or after clicking an epic) brings back the task list and the Detail pane.
- **The tree** lists the Markdown files of the docs folder, folders first, by name, with numbers compared as numbers (`0.9` before `0.10`). `Archive/`, `Epics/Tasks/` (the task files) and `Standard/` are left out. `Epics/` is in the tree with its EPIC files; `Epics/Completed/` is folded until clicked.
- **The document** is rendered with the epic view's renderer plus tables. Above it: its path and who changed it last, from git (author and date of the last commit that touched it; "not committed" when none).
- **Edit** swaps the rendered page for a plain text box with the file's text; **Done** writes the file and shows it rendered again. Text size A− / A+ applies, as in the Detail pane.
- **Linked** lists the project's open tasks whose description or done-when names the document's file name (`Design.md`); clicking one opens it in the task layout.
- **Linked can be closed** with × in its header; it folds to a thin rail at the right edge, which opens it again. Closed or open is kept per browser.
- **Column widths** of the document layout are dragged as on the Board, but kept apart from the task layout's: each layout remembers its own.
- Paths are always inside the docs folder: a path with `..`, an absolute path, or one into a hidden folder is refused. Only `.md` files are read or written.
- Docs are read and written in the project folder, not in an epic's worktree.
- Pictures in a document are not shown yet; the Confluence import epic (EPIC-009) brings them.

## Claude view

One page shows what Claude is working on, what it waits on Tabu for, and what changed. Everything on it comes from task data and the activity log; it keeps no state of its own.

- **Board / Claude** in the top bar switches the view and keeps the selected project. Claude carries a badge reading `<n> due`, the count of Tabu's tasks due within 7 days (the Board's "due within 7 days" filter on 🧑 tasks); its tooltip names each task it counts (number and title, with its deadline), and the same tasks are listed in the Claude view under Waiting on you.
- **Every warning says what is wrong, why, and what to do.** This holds for every badge, mark and message in the app, not only here.
- Three panes: **Working on now**, **Waiting on you** (Blocked on you, then Due within 7 days) with **Up next for Claude** below it, and **Activity log**.
- **Working on now:** AI tasks In progress. **Up next:** AI To-do tasks in rank order.
- No pane, and no line of the morning report, holds an open task of an epic that is not open (section Epics).
- **Due within 7 days:** Tabu's open tasks with a deadline 7 days away or nearer, soonest first: what the badge counts.
- **Blocked on you:** human To-do tasks with a `blocks: T-<id>` field naming the AI task they hold up. The field is set with `doit set <project>/<T-id> blocks=T-<id>` or in the Detail pane, and is kept in the task file.
- A card shows number, project pill, title and last change. A Waiting-on-you card also says why it is listed (`due in <n> days`, or `blocks T-<id>`) and what to do: the task's done-when, else the first line of its description. Clicking it opens that task on the Board.
- **Activity log:** every change to a task, from the CLI or the page, appends one line (time, project/task, what changed) to `activity.log` in the app's data folder. Lines older than 30 days are dropped on write. The pane shows the newest first.
- **Morning run:** a scheduled task in the Claude desktop app, 07:00 on weekdays, that runs `doit morning`. The command sweeps, then writes one report block to the activity log across all projects: tasks swept, AI tasks In progress, the top three AI To-do tasks, Blocked on you, and Tabu's tasks due within 7 days. It changes nothing beyond what the sweep does. It runs only while the app is open and the Mac awake.

## Marketing

Game profiles and contacts are built (EPIC-012); mail, festivals and campaigns are not. Doit becomes the marketing tool for every game and for Hidden by Design: who to contact, about which game, and which festivals to enter. The problem it solves is that outreach does not happen without a system, and time for it is short, so Doit picks the few relevant contacts and events and hides the rest.

When sitting down for outreach the order is festivals first, then people, then campaigns. The build order differs, because everything matches against the game profiles:

1. **Game profiles.** One per project that is marketed (a project with a kind and not marked not marketed, section Projects) (Bunny Bunker, Rapid Rocket Racing, Good Box and the others, Hidden by Design): genre tags, platforms, stage (in development, demo, released), release date, and what it needs now (wishlists, demo players, press). A profile's kind is its project's kind (section Projects). It is kept in the game's own project as `<docs>/Marketing/Profile.md`, and the game is that project's id; `doit profile add <project>` writes the template. A project with a kind but no file yet is offered like any other, with no mark; its profile is filled in the project's settings (section Projects), which write the file. A game without a Doit project keeps its profile as `Docs/Profiles/<game>.md` in the Polyspice Marketing project, with a `Kind:` line. Also editable as a doc, and tracked by the project's git.
   - **Drafted from docs.** For the marketed projects, Claude reads the project's design docs and writes its `Marketing/Profile.md` (genres, platforms, stage, release date, needs now), each field with an HTML comment naming its source doc, for Tabu to correct.
   - **The Marketing folder.** `<docs>/Marketing/` holds what marketing uses about a game: the profile, and each release's notes in `Marketing/Releases/<version>/`, so marketing finds everything in one place.
2. **Contacts.** A contact is a person, outlet or event. It has one or more types: influencer, blogger, press, publisher/distribution, tester, festival, conference (with a topic tag: game dev, podcast, design). Its fields: name, channels (kinds below), reddit, scales, scale note, checked date, email, reach (a follower count: the contact's largest audience on one channel, as last counted; Claude keeps it current while researching), genres (what the contact plays or covers, as tags like a profile's), about (a few lines on who the contact is and what they cover), notes, status (active, dormant, archived) and the games it fits.
   - **The contact pane** edits every field: channels are added, their URL changed and removed in place, and genres and about are set there as well as with `doit contact set`. Below the fields, **History** lists every touch and every sent draft to the contact, newest first, each with date, kind and game. **Last contact**, the date of the newest touch or sent draft, shows in the pane and on the contact's list row.
   - **The list** shows contacts as columns with headers: Name, Type, Reach, Status, Last contact, Next contact. A click on a header sorts by it, a second click reverses (Next contact: soonest first, empty last). **Next contact** is the full date, a parked contact's review date, marked when due; Last active (the newest reply or video touch) is in the contact pane.
   - **Special relationship.** A contact may carry a mark and a one-line reason (a friend, a past collaborator), set in the contact pane and with `doit contact set <id> special=<text>`; the list row and the pane show it.
   - **Scale labels.** The production scales a game or a creator's games sit at. A label describes production scale, funding, ownership or team structure, never quality. The labels are loose categories, so a creator or a game can carry more than one.
     - `solo`: made primarily by one developer; may still use purchased assets, freelancers or publishing support.
     - `indie`: independent development, often a small team; not a precise measure of budget or team size.
     - `triple-i` (III): independently funded, with ambitious scope or production values approaching AAA; the team may include developers experienced in large-studio work.
     - `aa`: a mid-sized production between indie and AAA in budget, team size and scope; the boundary is informal.
     - `aaa`: blockbuster scale, with large budgets, teams and marketing.
   - **Scale on profiles and contacts.** A game profile has a `Scale:` line (a list of labels, empty until Tabu sets it; `doit profile set <project> scale=indie,solo`). A contact has `scales`, the scales whose games the creator actually covers, a short `scale_note` (the evidence: counts from the last 20 uploads, whether a key route was found) and `checked`, the date the creator was last researched. These replace the free-text `Indie fit:` first line the research run wrote into `notes`.
   - **Relevant.** A contact is relevant by any of three paths: it has a fit for at least one game profile; its `scales` share a label with the `scale` of at least one profile; or its covered games (below) hold at least `COVERED_GAMES_MIN` (3) distinct games whose scale shares a label with a profile's scale, the "same league". Scale alone never decides fit: the covered list is the evidence. While no profile has a scale, only a fit makes a contact relevant. A festival or conference has no relevance.
   - **Covered games.** A contact has a list of the games the creator played, reviewed or streamed. An entry has the game's title, its scale labels (the same set), a kind (`played`, `reviewed` or `streamed`), a date, a source URL (the creator's own video, stream, VOD or post: primary evidence) and optional genre tags. `doit contact game add <id> <title> --scale a,b --kind k --date YYYY-MM-DD --source <url> [--genre a,b]` adds one; the same title again updates it; `doit contact game remove <id> <title>` drops it. An entry without a date and a source URL is refused: coverage known only from secondary sources goes in the notes. Shown in `contact show`, `--json` and the contact pane. Genre overlap between covered games and a profile is not a gate: it ranks `campaign suggest` and gives its reason.
   - **Why relevant.** Each contact carries `why`: the paths it is relevant by (fit, scale, or N covered games in our league). `doit contacts --relevant` prints it. A parked contact that has become relevant is listed by `doit contacts --parked --now-relevant`, read only: nothing is unparked automatically.
   - **Parked.** A fourth status beside active, dormant and archived. A contact that is not relevant to any game is set to `parked`, with `next` as the date it comes up for review. Parked contacts are left out of the default contact list, of `campaign contacts`, `campaign suggest` and the weekly outreach list (all of which pick only active contacts). Nothing is parked automatically: the relevance rule only reports who would be (`doit contacts --irrelevant`), and Tabu or the research run sets `status=parked`. The Contacts tab shows the active list as before and a separate collapsed **Parked** section under it, with a count.
   - **Per-channel facts.** A channel has a kind, a URL and, optionally, its followers and the date it was last active. Kinds: youtube, twitch, kick, tiktok, bluesky, x, instagram, facebook, reddit, discord, steam, patreon, podcast, rumble, website, linktree. The CLI writes one as `kind=url` or `kind=url|followers|date` (`youtube=https://youtube.com/@a|4.77M|2026-11-26`; followers as a count or `12k`, `1.2M`; an empty part is unknown). A host the importer does not know stays a `website`. `reddit` on the contact itself is the subreddit or user URL.
   - **Fit** links a contact to a game profile with a one-line reason. Claude decides fit, by researching the contact (what they play, how recently they post, their size) in batches of 20 to 30, largest reach first. Tabu corrects it.
   - **Games in the contact pane.** One block per game the contact fits or was contacted about: the game, its fit reason with a Remove button, and `contacted <date>` (the newest touch for that game) or `not contacted yet`. **+ Fit** picks a game and a reason. A fit is removed in the pane or with `doit fit <id> <game> --remove`.
   - **Filters** in the Contacts tab: type, reach, genre, status, **Fits** (a game) and **Contacted** (about a game, or not yet about a game). `doit contacts` takes `--fits`, `--contacted <game>`, `--not-contacted <game>` and `--no-about` (contacts Claude has not researched yet).
   - **Research by Claude.** Asked to research contacts, Claude takes a batch (`doit contacts --no-about`, largest reach first), reads their channels, and writes `about` (who they are, what they cover, how often they post), `notes` (what matters for outreach), genres and reach with `doit contact set`, and a fit per game with `doit fit`. This is a Claude run Tabu starts, not code in the app.
   - **Touches** replace the sheet's Replied and Posted Video columns: a log per contact of mails sent, replies and videos posted, each dated and tied to a game.
   - **Next contact** is a date on the contact; when it comes, the contact shows as due, for the games it fits.
   - First import: the Google Sheet `Marketing Contact List`, tab New Streamers (224 contacts, mostly YouTube). Every column is read: `Contact` is the email; Linktree, Youtube, Twitch, Steam, Discord, Bluesky (a bare `@handle` too), X, Instagram, Facebook and WWW are channels; a reach bucket (`A - Tiny >50` to `E - Huge >10.000`) is stored as its lower bound; `Genre` fills genres; dates such as `16-Sep-2025` are read; `Last Contact` becomes a dated mail touch. BB1 and BB2, old Bunny Bunker mailings, become mail touches for Bunny Bunker, dated where the cell holds a date. A re-import updates contacts in place, matched by email, then by a channel of one person (not Discord or a website), then by name.
   - **Storage:** SQLite, one file `marketing.db` in the app's data folder, through Node's built-in `node:sqlite` (Node 24, so no dependency). Contacts are personal data shared across projects and are queried more than read, so they are not files in a project's git. Tables: contacts, channels, fit (contact, game, reason), touches (contact, game, date, kind), events (the event of a festival or conference), drafts. Game profiles stay Markdown and are referred to by project id. The page and the CLI are the only ways in; Claude asks the CLI for a slice, as with tasks.
3. **Mail.** Doit uses Tabu's Google Workspace account over IMAP and SMTP, with an app password kept in the macOS Keychain.
   - Doit only reads one label, **Marketing**. Mail from an address on the contact list is moved there from Inbox and logged as a touch; other mail is never opened.
   - Sending: one template per pitch (game, hook, trailer, Steam link, the ask), plus one or two personal lines per contact that Claude drafts from the contact's research. Claude only writes drafts; Tabu approves each mail before Doit sends it. A copy lands in Marketing.
   - Sending and reply detection come first; reading full mail (attachments, HTML) after.
4. **Festivals and conferences.** Contacts of type `festival` or `conference` that also carry an event: `year` (one contact per name and year, so a rerun of the gathering updates and next year's edition is a new contact), `starts` and `ends` (dates), `deadline` (the application deadline), `cost` (text, `free` or `$100`), `where` (steam, epic, gog, itch, physical, online), `criteria` (`genres`, `stages` the event accepts: in development, demo, released, and `platforms`) and a watching state (watching, applied, accepted, declined, past). A conference also has a topic (game dev, podcast, design). A past event is set to `past`, never deleted. Sources: Steam, Epic, GOG and itch event pages and howtomarketagame.com/festivals (its Upcoming and New lists), gathered by a scheduled Claude task rather than code in the app. The task and its prompt live in the Polyspice Marketing project and write through the `doit festival` commands. Each run logs one activity line naming the festivals that are new since the last run; a source it could not read is named with the reason and what would fix it, never skipped silently.
   - **Events and Festivals.** A platform event (`where` is steam, epic, gog or itch: Next Fest, themed fests, sales) is listed under Events; every other festival and conference under Festivals. Selecting one shows its event fields in the pane (name, year, dates, deadline, cost, where, criteria, state), all editable there; contact fields such as reach, email and touches are not shown for it.
   - **The matching rule.** An event shows for a game when every criterion it gives holds against the game's profile: a genre in common, the game's stage among the stages, a platform in common (compared without case). A criterion left empty is not checked. An event with no criteria at all shows for every game, marked "criteria unknown". Past events and events whose deadline has passed are not offered for a game.
5. **Campaigns.** A campaign is an epic in the Polyspice Marketing project with a `Game:` line naming the projects it markets (games, applications or podcasts, comma-separated) and optionally an `Event:` line, a festival's id or a date (Bunny Bunker at Next Fest). Its tasks are steps and outreach. A campaign can be started around a release or around an event.
   - **The brief.** Header lines under `Status:`, each optional, from the usual campaign brief (objective, audience, key message, call to action, one primary measure with a target, channels, budget, timeline): `Occasion:` (release, demo, festival, update, sale, announcement, other: why now), `Goal:` (one sentence, the outcome), `Change:` (what should be different afterwards, from and to: `800 wishlists -> 3000`), `Measure:` (the one number that says it worked, with its target and date), `Audience:` (who it must reach), `Message:` (the one takeaway), `Ask:` (what the audience should do: wishlist, play the demo, cover the game), `Channels:` (mail to creators, press, Steam page, socials), `Starts:` and `Ends:` (dates), `Budget:`. `doit campaign add` takes each as a flag, `doit campaign set <project> <EPIC> key=value` changes one, `doit campaign show` prints the brief, so Claude can create and fill a campaign alone.
   - **Several projects.** + Campaign and `doit campaign add` take more than one project; Add contacts picks contacts that fit any of them. The campaign's For list is changed in its brief, in the page or with `campaign set game=a,b`.
   - **+ Campaign** in the Campaigns tab asks for the projects (checkboxes, one per marketed project), a name, an optional event and the occasion; the rest of the brief is filled in the campaign's pane afterwards, by Tabu or by Claude. **+ Campaign around this** on a festival or event opens the same form with the event chosen.
   - **Suggestions.** A campaign's pane lists the contacts Add contacts would pick (active, fit one of its games, not due after the event, not already on the campaign, largest reach first), each with its fit reason and when it was last contacted about the game, and an Add button per contact; and the open festivals and events that fit one of its games. `doit campaign suggest <project> <EPIC>` prints the same.
   - **Claude's runs.** The CLI steps Claude follows to research a batch of contacts and to create and fill a campaign from a release or an event are in `Marketing-Claude.md`.
   - **The contact field.** A task may carry `contact: <contact id>`. Ticking it done logs a touch (mail) on that contact for the campaign's game, with the task as its ref, so ticking it twice logs once.
   - **Add contacts.** On an open campaign, the button (or `doit campaign contacts`) makes one task per contact: `Reach out to <name>`, owner human, with the contact set. It picks contacts that are active, fit the game, are not due later than the event (a festival's start, else its deadline, or the date) and are not already on a task of the campaign, largest reach first, up to a limit (default 10). Nothing is added without that click or a Claude run.
   - **The weekly list.** Up to 5 contacts (open campaign tasks with a contact first, then contacts due for a game they fit, oldest due first), every festival whose deadline falls within 14 days and that fits a game, and up to 3 open campaign steps without a contact. It shows as the This week pane at the top of the Marketing view and as lines in the morning report; an empty week says `Outreach this week: nothing`.

**The Marketing top bar.** In the Marketing view the project chips and the Projects menu are gone, since contacts, drafts and festivals belong to no project. In their place are Marketing's own tabs in this order: **Campaigns**, **Contacts**, **Festivals**, **Events**, **Drafts**, **Overview**. There is no game picker in the top bar: a campaign says what it is for, Contacts filter by fit, and Festivals and Events have a game filter in their left pane. Campaigns shows the campaign list (open first) on the left, the selected campaign's brief (editable) and suggestions in the middle, and the contact pane on the right; the epic's tasks are on the Board (Open on Board). Contacts lists people only: festivals and conferences have their own tabs. Festivals and Events list what fits the game chosen in their filter, split as in step 4. In every list, arrow up and down move the selection and the pane follows. An empty list or pane says so in plain text in the pane's own font, with the button that fills it where there is one; it never shows a CLI command. Overview is the This week pane for every game. A profile is seen and edited in its project's settings, reached from the campaign's For list. The Board, Docs and Claude views keep the projects.

Left out: following people on social media to answer their posts. The platforms' APIs are closed or unstable; a recurring "check these people" task stands in for it.

**Open questions.**
- Each game's stage and its next festival or release date, which decides which profile comes first.

## Look

Blueprint: the board reads as a drafting sheet. It replaces the greyscale wireframe look; there is one style, no picker. Light and dark follow the system setting.

- **Colour.** Light: pale blue sheet (`#e6eef8`), near-white panes, navy ink (`#0f2a4a`), one technical blue for selection and lines (`#0b61d6`). Dark: navy sheet (`#0b2545`), deeper navy panes, pale blue ink, sky blue accent (`#7cc4ff`). Warning orange and success green stay semantic, apart from the accent.
- **Type.** IBM Plex Sans for text, IBM Plex Mono for numbers, ids, dates and labels.
- **Sheet.** A faint 20 px grid behind the panes, in the accent at about 8 % opacity.
- **Corners.** Panes, buttons, chips and pills have 2 px corners. Things that float or pass (popups, empty states, cards, forms, the error toast) keep 6 px corners, and the count badge is round, so they read as apart from the sheet.
- **Panes.** Outlined in the accent. Pane headers in mono capitals, accent coloured, with a small square bullet, over a dashed rule.
- **Rows and selection.** Rows divided by dashed rules, square corners. The selected row or epic gets an accent outline on a light accent fill. The active tab is underlined in the accent. A selected button, toggle or pill is filled in the slate blue (Detail column, below), not in ink: the view buttons, the list's owner filter, the In progress pill, the open document in the tree and the toggles of the Detail column. Two selected colours on one page would read as two meanings.
- **Progress.** Epic bars in the left pane are segmented like a scale rule, filled in the accent. Progress bars in the Detail column are filled in the slate blue, also where a wireframe draws them in black.
- **Detail.** The field block has a dashed outline instead of a grey fill.
- **Detail column.** The wireframes in `Docs/Design/Wireframes/detail-column/` fix the layout and content of the project, epic and task pages and the colours below. Type, corners, pane headers and the sheet are Blueprint there as everywhere.
  - No black for selected states or emphasis chips.
  - One muted slate blue for selected toggles, Decided chips, progress fills and the Comment button: light `#3D5677` with white text, dark `#8FA9CC` with `#0b2545` text (6.4 to 1).
  - The designer and Claude are told apart by a warm chip and a cool chip with different marks, 🧑 and 🤖 as on the list rows. Warm: light `#FCEFE3` with `#8F3F05`, dark `#4A2E14` with `#FFC89A` (8.3 to 1). Cool: light `#E8EEFA` with `#1A449E`, dark `#1D3F73` with `#BBD4FF` (7.0 to 1).
  - A Proposed chip is white with a dashed outline.
  - The dark ratios are computed, not seen on screen. Both dark chip fills sit close to the pane colour and may need an outline; EPIC-028's Check in play task judges that (check 5).
  - Six tokens carry these colours, each defined for light and dark, in `web/detail.css`.
- **Logo.** A checkmark in a circle over a drafting frame, cyan with orange crop marks, on a navy rounded square. The board shows it (`web/logo.svg`) before the name in the top bar and as the tab icon; the launcher uses the same logo in the macOS icon grid (`launcher/icon.svg`), which `launcher/build.sh` turns into the app icon, removing the applet's own asset catalog so macOS shows it. The logo keeps its own colours and is not themed.
- Every colour comes from a token defined for light and dark; no literal colour in a component rule.

The comparison of the five candidate styles, with this one as "Blueprint", is the private artifact `Doit Style Options` (claude.ai/artifact/L8qjksrvdhpyhEDjTd4unB).

## The CLI

`node bin/doit.js <command>`. Every command sweeps first (deadline and retention archiving). Output is one line per task, or JSON with `--json`.

- `projects`, `project add <name> <folder> [--docs Docs]`
- `list [--project <id>] [--epic EPIC-<nnn>] [--state open|active|backlog|done|archived] [--owner ai|human]`: default open tasks of every project, never archived ones unless asked. Open tasks of a parked, completed or archived epic are left out unless `--epic` names that epic (section Epics); `--json` carries `hidden` for each task.
- `show <project>/<T-id>`, `add <project> <EPIC-nnn> <title> [--owner] [--type] [--done-when] [--deadline] [--state] [--agent] [--model] [--effort]`, `set <project>/<T-id> key=value ...` (among the keys `agent`, `model` and `effort`; an empty value clears one), `comment <project>/<T-id> <text> [--as human]`, `epic add <project> <name>`, `epic close <project> <EPIC-nnn>` (archives the epic's completed task files and leaves its open ones hidden, sets it Done, writes its `Closed:` date and moves it to Completed/), `sweep`, `morning` (sweeps and writes the morning report to the activity log, section Claude view).
- Contacts (section Marketing): `contacts [--type t] [--fits <game>] [--genre g] [--status s] [--due] [--reach <n>] [--json]` (one line per contact: id, name, types, reach, status, next contact with `due` marked, the games it fits; due first, then largest reach), `--reach <n>` keeps contacts with a reach of at least n; `contacts import <file>` (the New Streamers CSV, every column read as section Marketing, step 2 says: an A to E reach band is stored as its lower bound; a re-import updates in place), `contact show <id> [--json]`, `contact add <name> --type a,b [--email] [--reach] [--topic] [--notes] [--status] [--next] [--channels kind=url,...]`, `contact set <id> key=value ...`, `fit <id> <game> <reason>`, `touch <id> mail|reply|video [--game] [--date]`, `profiles`. A refused value prints the message and exits 1.
- Festivals (section Marketing): `festivals [--fits <game>] [--deadline-within <days>] [--state s] [--json]` (one line per festival or conference: id, name and year, deadline with days left, cost, where, watching state; by deadline, past-state ones hidden unless `--state past`; `--fits` keeps those whose criteria match the game's profile and whose deadline has not passed, and marks `criteria unknown`; `--deadline-within n` keeps deadlines from today to n days ahead), `festival upsert <name> --year <y> [--type] [--topic] [--starts] [--ends] [--deadline] [--cost] [--where] [--genres] [--stages] [--platforms] [--url] [--notes] [--state]` (finds the festival by name and year and updates only the fields given, else adds it, so a rerun never duplicates), `festival set <id> state=<state>`.
- Mail (section Marketing): `templates`, `draft add <contact id> --template <name> --game <game> --personal <text>` (prints the draft id and the filled mail), `draft show <id> [--json]`, `drafts [--state s] [--json]`, `mail sweep` (logs replies from contacts as touches and moves them to Marketing). Nothing in the CLI approves or sends: Tabu does that in the page.
- Campaigns (section Marketing): `campaign add <project> <name> --game <game> [--event <festival id|YYYY-MM-DD>]` (prints the epic id), `campaign contacts <project> <EPIC-nnn> [--limit n]` (makes the contact tasks, prints each ref and contact), `outreach [--json]` (the weekly list). `add ... --contact <id>` and `set ... contact=<id>` tie a task to a contact; an unknown id is refused.

## Running it

`launcher/Doit.app` (built by `launcher/build.sh`) is a stay-open applet: double-click starts the server and opens `http://localhost:4317`; quitting it stops the server. If a server is already running on the checked-out commit, it only opens the page; one on another commit (`GET /api/version`) is stopped and the current code started. No terminal is needed.

## Data

- The project list and settings: `~/Library/Application Support/Doit/settings.json` (`DOIT_HOME` overrides it). Kept until deleted.
- The activity log: `activity.log` beside the settings, 30 days.
- Tasks and epics: Markdown in each project's docs folder, tracked by that project's git. Nothing leaves the machine. No personal data beyond names Tabu types.
- Contacts: `marketing.db` beside the settings (SQLite): names, emails, channel links and notes of marketing contacts. Personal data, kept only in the data folder and in no project's git. Mail drafts are in the same file (table `drafts`: contact, game, template, personal lines, subject, body, state, sent time, Message-ID, error, whether the copy is labeled Marketing); a touch also carries a note (the mail subject) and a ref (the Message-ID, so a mail is never logged twice).
- Mail account: settings key `mail` (`address`, `name`, `dailyCap`, default 20). The app password is in the macOS Keychain (generic password, service `doit-mail`, account the address), never in a file.
